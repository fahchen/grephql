**Feature**: client/features/compile_time_validation.feature
**Rule**: Schema is loaded at compile time from the configured source

Follows on from [BDR-0005](BDR-0005-fork-absinthe-parser.md), which decided to fork the parser in the first place.

## Context

TypedGql vendors two files from [Absinthe](https://github.com/absinthe-graphql/absinthe) (MIT, see `NOTICE`). Everything else in the parse pipeline is our own code that happens to consume the vendored output.

| File | Origin | Kind |
|---|---|---|
| `lib/typed_gql/lexer.ex` | `lib/absinthe/lexer.ex` | vendored, patched |
| `src/typed_gql_parser.yrl` | `src/absinthe_parser.yrl` | vendored, patched |
| `lib/typed_gql/parser.ex` | `lib/absinthe/phase/parse.ex` | ours, derived — same control flow, but returns error strings instead of `%Phase.Error{}` and drops Blueprint, `Language.Source`, options and the `try/rescue` |
| `lib/typed_gql/language.ex`, `lib/typed_gql/language/*.ex` | — | ours (AST structs the grammar instantiates by name) |
| `src/typed_gql_parser.erl` | — | generated by the `:yecc` compiler, git-ignored |

The vendored files carry local patches, so every upstream pull is a conflict waiting to happen. GraphQL's grammar is stable, so pulls are rare — which is exactly what makes an implicit process dangerous: by the time the next one happens, nobody remembers why the local lines look the way they do.

## Behaviours Considered

### Option A: Freeze the fork
Never sync. The grammar is stable and the current copy works.

### Option B: Track upstream as a git subtree or vendor branch
Let git merge upstream changes into the patched files automatically.

### Option C: Copy the upstream file and hand-re-apply a documented divergence list
Each local deviation is recorded here with its reason, and re-applied deliberately after every copy.

## Decision

Chose Option C, with the divergence list, sync procedure, and post-sync invariants recorded below.

Last verified against Absinthe `main` at commit `de0e411f` (2026-07-14, v1.11.0 + 7 commits, `@version "1.12.0"`), on 2026-08-13 from a fresh clone: that commit is upstream's current `main` HEAD, and both vendored files match it except for the divergences listed below.

## Reason

Hand-re-applying forces a human to look at each divergence against the new upstream text. Four of the twelve hunks exist because a location is silently lost otherwise, and a fifth because a whole field is — failure modes with no compile error and no test failure inside Absinthe itself, since Absinthe reports errors from its own phases while TypedGql reports them at compile time with a line and column. A merge that "succeeds" while quietly reordering an `extract_binary/1` call is exactly the outcome to avoid, and there are only eight divergences to re-apply.

## Rejected Alternatives

**Option A** — Freezing means upstream lexer fixes (unicode handling, block-string edge cases, token limits) never arrive, and the divergences stay undocumented, which is the current risk rather than a fix for it.

**Option B** — A three-way merge hides exactly the case that matters: upstream rewriting the rule that a divergence sits in. It succeeds silently and the location regression only shows up as a worse error message months later.

## Sync procedure

1. Get the upstream files for the target ref (a release tag, or `main` if you want unreleased grammar fixes):

   ```bash
   git clone https://github.com/absinthe-graphql/absinthe /tmp/absinthe
   git -C /tmp/absinthe checkout v1.11.0   # or a newer tag / main
   ```

2. Diff each vendored file against its upstream counterpart. Every hunk that appears must be one of the divergences listed below — anything else is upstream drift you need to fold in:

   ```bash
   diff -u /tmp/absinthe/lib/absinthe/lexer.ex lib/typed_gql/lexer.ex
   diff -u /tmp/absinthe/src/absinthe_parser.yrl src/typed_gql_parser.yrl
   ```

3. Back up both files first (`cp lib/typed_gql/lexer.ex /tmp/lexer.bak`, same for the grammar), then copy the upstream file over ours — exactly the two vendored files, nothing else — and re-apply the divergences below by hand. `lib/typed_gql/parser.ex` and the `TypedGql.Language.*` structs are ours; they are touched only when upstream changed a shape they consume (invariants 3 and 5). When step 2 found no upstream changes, `diff` against the backup must come out empty: that proves the divergence list here is complete, with no undocumented local edit silently dropped.

4. Check the invariants (next section), then verify:

   ```bash
   mix compile --warnings-as-errors   # regenerates src/typed_gql_parser.erl
   mix precommit                      # format, credo, dialyzer, full test suite
   mix test --cover                   # coverage threshold is 100%
   ```

5. Update `NOTICE` if the set of adapted files changed, and update the "Last verified against" line above.

## Invariants to check after every sync

1. **Lexer keyword tokens ↔ grammar terminals.** Every entry in the lexer's `@reserved_words` must be declared as a keyword terminal in the grammar, and vice versa. A reserved word with no terminal makes an otherwise valid name unparseable (this is exactly how `ON` broke — see divergence L2).

   ```bash
   awk '/^Terminals/,/\.$/' src/typed_gql_parser.yrl
   rg -A20 '@reserved_words' lib/typed_gql/lexer.ex
   ```

2. **Token shapes ↔ extraction helpers.** Reserved words lex to a 2-tuple `{atom, {line, column}}`; value-carrying tokens lex to a 3-tuple `{atom, {line, column}, chars}`. `extract_binary/1` and `extract_location/1` in the grammar's Erlang section have a clause per shape. A production that converts a token to a binary *before* the AST node is built silently loses its location, because `extract_location/1` falls through to `_Other -> #{line => nil, column => nil}`.

3. **`build_ast_node('X', ...)` ↔ `TypedGql.Language.X`.** The grammar builds structs by name through `'Elixir.Kernel':struct/2`, which **silently drops unknown keys**. If upstream adds a field to an AST node and our struct lacks it, nothing fails — the data just disappears. Compare the key sets after any grammar change.

4. **Lexer and yecc error tuples ↔ `lib/typed_gql/parser.ex`.** Our wrapper matches the same error shapes upstream's `Absinthe.Phase.Parse` does: `{:error, rest, loc}` and `{:error, :exceeded_token_limit}` from the lexer, `{{line, column}, :typed_gql_parser, messages}` from yecc. If upstream adds or reshapes a case there, mirror it. Two upstream cases are currently *not* mirrored: the integer-only location tuple `{line, :absinthe_parser, msgs}` (yecc emits it, so `TypedGql.Parser.parse/1` raises `FunctionClauseError` — `lib/typed_gql/formatter.ex` rescues it as a workaround) and the `{:ok, []} -> empty Document` short-circuit for blank input.

5. **Downstream consumers of the AST.** `lib/typed_gql/printer.ex` (executable documents only — it does not print SDL type definitions), `lib/typed_gql/formatter.ex`, `lib/typed_gql/validator/**`, `lib/typed_gql/type_generator.ex`, `lib/typed_gql/input_type_generator.ex`, `lib/typed_gql/compiler.ex`, `lib/typed_gql/macros.ex`, `lib/typed_gql/generation/**`. `lib/typed_gql/schema/parser.ex` is *not* affected: it reads introspection JSON, never the grammar.

## Divergences from upstream

### G1 — AST namespace

```diff
--- a/src/absinthe_parser.yrl
+++ b/src/typed_gql_parser.yrl
 build_ast_node(Type, Node, Loc) ->
-  'Elixir.Kernel':struct(list_to_atom("Elixir.Absinthe.Language." ++ atom_to_list(Type)), Node#{loc => Loc}).
+  'Elixir.Kernel':struct(list_to_atom("Elixir.TypedGql.Language." ++ atom_to_list(Type)), Node#{loc => Loc}).
```

**Why**: the whole point of the fork (BDR-0005) is our own AST structs without depending on Absinthe. This hunk is what makes the vendored grammar build them.

### G2 — Enum values and names spelled `on` keep their location

The three hunks below move `extract_binary/1` from the `EnumValue` production down to its consumers, and stop collapsing the `on` token early. They must be applied together.

```diff
--- a/src/absinthe_parser.yrl
+++ b/src/typed_gql_parser.yrl
 Name -> NameWithoutOn : '$1'.
-Name -> 'on' : extract_binary('$1').
+% Kept as the raw token (not extract_binary/1) so that a name spelled `on`
+% carries a location like every other name.
+Name -> 'on' : '$1'.

-Value -> EnumValue :     build_ast_node('EnumValue',    #{'value' => '$1'},  extract_location('$1')).
+Value -> EnumValue :     build_ast_node('EnumValue',    #{'value' => extract_binary('$1')},  extract_location('$1')).

-ValueConst -> EnumValue :     build_ast_node('EnumValue',    #{'value' => '$1'},  extract_location('$1')).
+ValueConst -> EnumValue :     build_ast_node('EnumValue',    #{'value' => extract_binary('$1')},  extract_location('$1')).

-EnumValue -> Name : extract_binary('$1').
+% Passes the token through so both consumers (Value/ValueConst and
+% EnumValueDefinition) can read its location; each extracts the binary itself.
+EnumValue -> Name : '$1'.
```

**Why**: upstream reduces `EnumValue` to a bare binary, so `extract_location/1` hits its catch-all and every `%EnumValue{}` comes back with `loc: nil`. The same reduction also costs `%EnumValueDefinition{}` (SDL `enum Role { ADMIN }`) its location, since that production reads the location off `EnumValue` too. `Name -> 'on'` has the identical problem for any field, argument, enum value, or type named `on`.

Passing the token through is free: `extract_binary/1` already accepts both the 2-tuple keyword shape and the 3-tuple name shape, and every other consumer of `Name` (`Field`, `NamedType`, `Alias`, all the SDL definitions, …) already calls `extract_binary/1` itself.

**Do not** re-introduce a post-parse location fixup instead. That was tried: it needed ~76 lines to walk the document and re-match enum nodes against the token stream by position, it could not recover `EnumValueDefinition` locations, and it still missed `on` (a keyword token, absent from the `:name` token stream).

### G3 — Variable definitions keep their directives

```diff
--- a/src/absinthe_parser.yrl
+++ b/src/typed_gql_parser.yrl
-VariableDefinition -> Variable ':' Type DirectivesConst: build_ast_node('VariableDefinition', #{'variable' => '$1', 'type' => '$3'}, extract_child_location('$1')).
+% Keeps the directives, like the DefaultValue production below already does.
+VariableDefinition -> Variable ':' Type DirectivesConst: build_ast_node('VariableDefinition', #{'variable' => '$1', 'type' => '$3', 'directives' => '$4'}, extract_child_location('$1')).
```

**Why**: this is an upstream bug, not a feature — expect a sync to re-introduce it, and re-apply this hunk.

The spec's `VariableDefinition : Variable : Type DefaultValue? Directives[Const]?` allows directives with or without a default value. Upstream keeps them in only one of the two productions: the rule above parses `DirectivesConst` and then drops it on the floor, while the `DefaultValue DirectivesConst` rule two lines down writes `'directives' => '$5'`. So `query ($x: Int @lower)` silently loses `@lower`, but `query ($x: Int = 1 @lower)` keeps it — an asymmetry with no reading of the spec behind it.

Both productions arrived together in Absinthe [#1145](https://github.com/absinthe-graphql/absinthe/pull/1145) (`b298824e`), which split `Value[Const]` out of `Value`. Before it, directives without a default value were not parseable at all, so nothing regressed — the new rule was simply written without the key.

Without this hunk `TypedGql.Validator.Rules.Directives` is half-blind: `validate_variable_definition_directives/3` only ever sees a non-empty list for the default-value spelling, so an `@skip` on a variable definition goes unreported in the more common one.

### G4 — `repeatable` is a legal name

```diff
--- a/src/absinthe_parser.yrl
+++ b/src/typed_gql_parser.yrl
 NameWithoutOn -> 'directive' : '$1'.
+% GraphQL keywords are contextual: `repeatable` is only a keyword inside a
+% directive definition, and is a legal name everywhere else.
+NameWithoutOn -> 'repeatable' : '$1'.
```

**Why**: this is an upstream bug, not a feature — expect a sync to drop it, and re-apply this hunk. Same shape as L2: the lexer emits a dedicated token that no `Name` production accepts, so `query { repeatable }` fails to parse against a schema that declares such a field.

`true`, `false` and `null` have the identical problem and are **deliberately not fixed**. Adding them to `NameWithoutOn` puts them in both value and name position, which LALR(1) cannot separate — `{a: null}` is ambiguous between `ObjectField -> Name ':' Value` and a null value — and yecc reports 118 reduce/reduce conflicts. Supporting them needs a grammar restructure, not a divergence hunk.

### G5 — A leading pipe is allowed on a one-entry list

```diff
--- a/src/absinthe_parser.yrl
+++ b/src/typed_gql_parser.yrl
 UnionMembers -> '|' NamedType '|' UnionMembers : ['$2'|'$4'].
+% A leading pipe is permitted on a one-entry list too.
+UnionMembers -> '|' NamedType : ['$2'].

 DirectiveDefinitionLocations -> '|' Name '|' DirectiveDefinitionLocations : [extract_binary('$2')|'$4'].
+% A leading pipe is permitted on a one-entry list too.
+DirectiveDefinitionLocations -> '|' Name : [extract_binary('$2')].
```

**Why**: this is an upstream bug, not a feature — expect a sync to drop it, and re-apply this hunk. The spec's `UnionMemberTypes: = |? NamedType` and `DirectiveLocations: |? DirectiveLocation` allow the pipe before a single entry, but upstream only has the recursive production, so `union Search = | User` and `directive @d on | FIELD` fail at EOF.

### L1 — Module name and attribution header

```diff
--- a/lib/absinthe/lexer.ex
+++ b/lib/typed_gql/lexer.ex

+# Adapted from Absinthe.Lexer (https://github.com/absinthe-graphql/absinthe)
+# Original work Copyright (c) 2015 CargoSense, LLC — MIT License
+# See NOTICE file for attribution details.

```

**Why**: namespacing, plus the MIT attribution required by the licence. The same header is on `lib/typed_gql/parser.ex`.

### L2 — `ON` is not a reserved word

```diff
--- a/lib/absinthe/lexer.ex
+++ b/lib/typed_gql/lexer.ex
   @reserved_words ~w(
     null
     on
-    ON
     query
```

**Why**: this is an upstream bug, not a feature — expect a sync to re-introduce it, and delete it again.

GraphQL is case-sensitive, and its keywords are contextual rather than reserved: only lowercase `on` is the fragment keyword (the spec's `FragmentName: Name but not "on"`, which the grammar models as `NameWithoutOn`). `ON` is an ordinary `Name`, legal as a field name, enum value, or fragment name — and `ON`/`OFF` are common enum values in real schemas.

Upstream lexes `ON` as an `:ON` token that no grammar rule can accept: `ON` entered `@reserved_words` in Absinthe's 2018 SDL Support commit (`01be95b5`, #503), and `git log -S"'ON'" -- src/absinthe_parser.yrl` shows an `'ON'` terminal has never existed in the grammar's entire history. So `query { ON { x } }`, `query { f(role: ON) { x } }` and `fragment ON on User { name }` all fail with `syntax error before: 'ON'`.

Deleting the reserved word makes `ON` lex as a plain `:name` and take exactly the same path as any other name — no special case. The alternative, declaring an `'ON'` terminal plus a `NameWithoutOn -> 'ON'` rule, adds a second spelling to every `Name` consumer for no gain. Regression tests: `test/typed_gql/lexer_test.exs` ("uppercase ON is a plain name") and `test/typed_gql/parser_test.exs` ("`ON` is an ordinary name, not the fragment keyword").

### L3 — `line_and_column/3` is private

```diff
--- a/lib/absinthe/lexer.ex
+++ b/lib/typed_gql/lexer.ex
-  def line_and_column({line, line_offset}, byte_offset, column_correction) do
+  defp line_and_column({line, line_offset}, byte_offset, column_correction) do
```

**Why**: nothing outside the lexer calls it, and a public function with no caller is dead public API (`mix credo --strict` and the 100% coverage threshold both flag it).

## Not vendored

Only the lexer and the grammar. Absinthe's phases, blueprint, schema, and execution layers are irrelevant to a client library — see BDR-0005's rejected Option A. The `TypedGql.Language.*` structs are ours; they are deliberately narrower than `Absinthe.Language.*` (no `errors`, no `flags`, and `FieldDefinition` keeps a `complexity` field that the grammar never sets). `TypedGql.Language.SchemaDefinition` is currently unused — the grammar builds `SchemaDeclaration` for `schema { ... }`.
